## -1. 核心原则
- 第一性原理：从原始需求出发，动机不清立即停止，路径非最优则直接纠正。
- 极简沟通：用简单直白的中文一次性输出，把用户当高中生，拒绝使用过多的语言混杂、术语堆砌。
- Let it crash: 发现问题尽早暴露，严禁使用任何降级、兜底、启发式补丁或非严谨通用算法的后处理补救。
- 自检与精简：每次改动后，严格执行【Review查bug然后第一性原理分析】流程，思考是否有更简单、更稳健的实现。
- 理论指导：每一部分设计都需要基于具体理论，同时涉及教育理论的地方需要进行web search了解理论具体内容，切忌望文生义。

## 0. 项目定位

本项目面向 **EEDI 长链路学生-教师交互仿真**。

目标不是做：
- 通用聊天学生代理
- 任意任务模拟
- 单轮问答生成

而是做：

> 给定一道数学题、一个真实教师-学生历史交互上下文，构建一种理论约束下的学生状态转移仿真方法，使大模型生成的“下一轮学生反应”在状态变化、错误路径连续性、提示吸收节奏和表达成熟度上更接近真实学生，并减少“一点就通”“突然成熟”“错误路径断裂”等失真。

本项目的核心不是“直接扮演学生”，而是：

> 先做第三人称学生状态解析与状态转移预测，再在该预测状态下生成学生下一轮回复。

---

## 1. 方法总览

本项目方法采用一个 **Long-chain Student Simulation Harness**。

主链路如下：

`DialogueContext -> StudentContextProfile -> TutorMoveProfile -> InteractionState -> StateTransitionPrediction -> ConstraintBundle -> StudentTurnGeneration -> DynamicViolationCheck -> Optional One-Step Retry`

其中：

1. `DialogueContext`
   - 当前题目
   - 当前轮之前的 tutor-student 交互历史
   - 当前轮教师发言

2. `StudentContextProfile`
   - 从历史交互中抽取出的“当前学生画像”，是交互内生的学生表征，不假设有额外完整静态画像

3. `TutorMoveProfile`
   - 对教师当前动作的理论化解析

4. `InteractionState`
   - 当前这一轮学生的局部认知/调节/参与状态

5. `StateTransitionPrediction`
   - 在当前教师动作下，学生状态将如何变化

6. `ConstraintBundle`
   - 将状态转成行为边界

7. `StudentTurnGeneration`
   - 在边界内生成下一轮学生回复

8. `DynamicViolationCheck`
   - 检查是否发生动态失真

9. `Optional One-Step Retry`
   - 若越界，仅允许一次局部重试

---

## 1.1 单步 step-by-step 生成协议

这里的 `think step by step` 不是“先把这一轮完整想完，再拆成几段输出”。

这里要求的是严格的单步生成协议：

1. 每次只允许模型推进当前轮里的一个内部小步骤。
2. 每一步只能使用当前时点已经可见的信息，不能偷看未来轮次信息、官方标注或后验答案。
3. 每一步都必须服从第三人称状态层和约束层，不能绕过 `InteractionState -> StateTransitionPrediction -> ConstraintBundle` 直接成熟作答。
4. 中间步骤不得直接产出完整、成熟、收束过度的最终学生回复。
5. 只有最后一步才允许输出当前轮最终 `student turn`。
6. 如果步数预算耗尽后仍无法形成合法回复，必须显式失败，不能把半成品伪装成最终答案。
7. 每一步的输入、状态、输出都应实时落盘，保证可续跑、可审计、可复盘。

这个协议的作用，是硬性抑制“一点就通”“突然成熟”“先想完再伪装成逐步推进”这几类常见失真。

## 2. 非目标（必须写清楚）

本项目不做：

1. 不做“直接 student roleplay”
2. 不做“给模型一段长学生画像，然后直接让它继续聊天”
3. 不做“根据真实学生下一轮答案反向提示模型”
4. 不做“为了贴近真实学生而对特定题目、特定轮次写特判”
5. 不做“显式告诉模型这一轮应该学会/不应该学会”
6. 不做“把理论粗暴压成 low/medium/high 再假装是原理论分类”

## 3. 理论框架

本项目的动态方法依赖五类理论资源。

### 3.1 Vygotsky / ZPD / Scaffolding
用途：
- 判断学生当前与任务及当前帮助之间的位置关系
- 判断教师这一步帮助是否足以支持学生发生合理变化

本项目中用于支持：
- `competence_position`
- `help_internalization_state`
- 动态失真中的 `over_fast_transition`

### 3.2 Conceptual Change / Misconception Research
用途：
- 刻画学生错误观的持续、扰动、松动与解决
- 保证错误路径在多轮中有连续性

本项目中用于支持：
- `misconception_status`
- 动态失真中的 `error_path_discontinuity`

### 3.3 Zimmerman Self-Regulated Learning (SRL)
用途：
- 刻画学生在交互中的监控、调节、修正、坚持
- 解释为什么有些学生并非不会，而是缺乏监控和修正能力

本项目中用于支持：
- `metacognitive_regulation_state`
- 部分 `response_commitment_state`
- 动态失真中的成熟化判断

### 3.4 ICAP
用途：
- 约束学生当前回复表现出的外显参与层级
- 防止学生在并未真正内化的情况下表现出过高层次的解释性参与

本项目中用于支持：
- `engagement_form`
- 动态失真中的 `over_mature_response`

重要说明：
ICAP 有原生类别，因此本项目必须 **exactly same** 使用：
- Passive
- Active
- Constructive
- Interactive

### 3.5 Bandura Self-Efficacy + Pekrun Control-Value Theory
用途：
- 提供对当前承诺状态、控制感、任务价值感的理论解释
- 支持为什么某些学生在同样提示下更不愿表态、更容易退缩或更快承诺

重要说明：
这两类理论本身不是固定离散标签集合，因此本项目不能把它们伪装成理论原生 low/medium/high 分类。
它们只能在 prompt 中作为**理论化描述任务**出现。

## 4. 三层变量体系（必须分清）

### 4.1 Theory-native categories
只有理论本身有明确类别时，才允许使用原生分类。

本项目目前只在以下地方允许：

#### ICAP
- Passive
- Active
- Constructive
- Interactive

#### 如后续需要 task-side complexity，可允许：
- Webb DOK
- TIMSS cognitive domains
但当前 EEDI 长链主任务中，这不是最核心层。

### 4.2 Theory-grounded descriptive outputs
理论本身不是固定类别，但可以要求模型基于理论做描述性判断。

例如：
- self-efficacy analysis
- control appraisal analysis
- value appraisal analysis
- SRL phase/process analysis

这些不能伪装成理论原生枚举。

### 4.3 Method-level states
这是本项目自己的状态空间，不是原理论原词，但必须由理论约束。

例如：
- `competence_position`
- `misconception_status`
- `metacognitive_regulation_state`
- `help_internalization_state`
- `response_commitment_state`
- `response_maturity_cap`

### 5.2 StudentContextProfile

这是从历史交互中抽取出来的“当前学生画像”，不是外部静态学生档案。

```python
StudentContextProfile(
    self_efficacy_analysis: dict,
    srl_analysis: dict,
    control_value_analysis: dict,
    engagement_tendency_analysis: dict,
    response_style_analysis: dict,
    evidence_trace: list[str]
)
```

#### 必须包含的字段

##### self_efficacy_analysis

理论：Bandura
输出：

* `efficacy_belief_description`
* `efficacy_belief_evidence`

##### srl_analysis

理论：Zimmerman SRL
输出：

* `primary_srl_vulnerability`
* `srl_process_evidence`

说明：
这里不要伪装成 low/medium/high。
应围绕原理论阶段或子过程来描述，例如：

* Forethought vulnerability
* Performance-phase monitoring weakness
* Self-reflection weakness

##### control_value_analysis

理论：Pekrun CVT
输出：

* `control_appraisal_description`
* `value_appraisal_description`
* `control_value_evidence`

##### engagement_tendency_analysis

理论：ICAP
输出：

* `engagement_level_tendency`
* `engagement_evidence`

这里必须使用 ICAP 原生类别：

* Passive
* Active
* Constructive
* Interactive

##### response_style_analysis

这是实现层辅助分析，不假装是理论原生类目。
输出：

* `response_directness_description`
* `response_directness_evidence`

### 5.3 TutorMoveProfile

这是动态任务里必须新增的核心对象。

```python
TutorMoveProfile(
    instructional_intent: str,
    support_type: str,
    support_intensity: str,
    support_granularity: str,
    support_contingency: str,
    responsibility_shift: str,
    target_of_intervention: str,
    uptake_expectation: str,
    move_evidence: list[str]
)
```

#### 说明

这里不要求你必须把每个字段都挂到一个单独理论原生分类上，但它们整体要受 ZPD / scaffolding 理论约束。

建议字段含义：

* `instructional_intent`

  * 教师是在纠错、追问、提示、重述、拆步、鼓励解释，还是直接推进答案

* `support_type`

  * 如：

    * conceptual_hint
    * procedural_hint
    * answer_elicitation
    * error_challenge
    * explanation_request

* `support_intensity`

  * 这里允许方法层离散值：

    * weak
    * medium
    * strong
      但必须在 prompt 中解释其含义，不假装是理论原生分类

* `support_granularity`

  * 教师这一步是在给一个最小线索、一个局部步骤，还是更长的多步支架

* `support_contingency`

  * 教师这一步和学生当前已暴露状态贴得有多紧

* `responsibility_shift`

  * 当前这一步是 tutor 继续托着、和学生共同承担，还是开始把责任推回学生

* `target_of_intervention`

  * 教师当前主要在处理：

    * misconception
    * missing_step
    * confidence
    * commitment
    * explanation_depth

* `uptake_expectation`

  * 当前这类帮助理论上最可能带来：

    * no_change
    * local_update
    * partial_restructuring
    * strong_restructuring

说明：
这些是**支架理论约束下的动作画像**，不是原生理论标签。

### 5.4 InteractionState

这是最关键的当前学生局部认知状态层。

```python
InteractionState(
    competence_position: str,
    misconception_status: str,
    metacognitive_regulation_state: str,
    help_internalization_state: str,
    help_seeking_state: str,
    attempt_readiness: str,
    engagement_form: str,
    response_commitment_state: str,
    response_maturity_cap: str,
    state_evidence: list[str]
)
```

#### 字段定义与理论依据

---

#### 5.4.1 `competence_position`

理论依据：

* Vygotsky / ZPD / scaffolding

方法层分类：

* `within_current_competence`
* `within_zpd`
* `beyond_zpd`

定义：

* `within_current_competence`

  * 学生当前无需额外帮助即可完成或基本完成
* `within_zpd`

  * 学生当前在适量帮助下有可能推进
* `beyond_zpd`

  * 当前这一步帮助仍不足以把学生带到可完成状态

说明：
这不是理论原生术语逐字分类，但完全由 ZPD 推导出来。

---

#### 5.4.2 `misconception_status`

理论依据：

* conceptual change
* misconception continuity

方法层分类：

* `not_salient`
* `active_misconception`
* `destabilizing_misconception`
* `resolved_misconception`

定义：

* `not_salient`

  * 当前未见明显错误观主导
* `active_misconception`

  * 错误观正在支配理解
* `destabilizing_misconception`

  * 错误观开始被扰动，但尚未真正解决
* `resolved_misconception`

  * 相关错误观已明显被修正

说明：
这不是某个单篇理论中的原生离散表，但它是概念改变理论下合理、可审计的状态化定义。

---

#### 5.4.3 `metacognitive_regulation_state`

理论依据：

* Zimmerman SRL
* metacognitive monitoring

方法层分类：

* `unmonitored`
* `weak_monitoring`
* `active_monitoring`
* `self_correcting`

定义：

* `unmonitored`

  * 学生几乎没有体现对自己思路的监控
* `weak_monitoring`

  * 学生隐约知道有问题，但监控和修正都很弱
* `active_monitoring`

  * 学生能明显监控当前过程
* `self_correcting`

  * 学生已出现主动修正倾向

说明：
这不是 Zimmerman 原理论原生类别，但它是由 SRL 中 performance/self-reflection 过程推导出来的实现状态。

---

#### 5.4.4 `help_internalization_state`

理论依据：

* scaffolding
* ZPD
* internalization

方法层分类：

* `no_uptake`
* `surface_uptake`
* `partial_internalization`
* `integrated_internalization`

定义：

* `no_uptake`

  * 教师帮助几乎未被吸收
* `surface_uptake`

  * 学生仅吸收表面提示语句
* `partial_internalization`

  * 学生已将部分提示转化为自己的局部理解
* `integrated_internalization`

  * 学生基本将帮助整合进当前理解结构

说明：
这是动态学生仿真最关键的状态之一，直接对应“为什么真实学生不会一点就通”。

---

#### 5.4.5 `help_seeking_state`

理论依据：

* Zimmerman SRL
* adaptive help seeking

方法层分类：

* `help_avoidant`
* `help_ambivalent`
* `adaptive_help_seeking`

定义：

* `help_avoidant`

  * 学生当前倾向于不求助，即使已经卡住
* `help_ambivalent`

  * 学生有局部求助倾向，但仍犹豫或只会弱表达
* `adaptive_help_seeking`

  * 学生更可能提出与当前卡点相关的有效求助

说明：
这不是“有没有问号”这种表面行为标签，而是当前学生对求助的调节姿态。

---

#### 5.4.6 `attempt_readiness`

理论依据：

* scaffolding
* ZPD
* SRL performance phase

方法层分类：

* `not_ready`
* `ready_for_local_attempt`
* `ready_to_revise`

定义：

* `not_ready`

  * 学生当前还没准备好进入实质尝试，更多处在卡住、确认或求助阶段
* `ready_for_local_attempt`

  * 学生可以做一个局部尝试，但还不支持成熟完整推理
* `ready_to_revise`

  * 学生更可能对已有想法做局部修正，而不是从零开始成熟作答

说明：
它描述的是“学生此刻能不能尝试、能尝试到哪一步”，不是任务接口格式。

---

#### 5.4.7 `engagement_form`

理论依据：

* ICAP

这里必须 exact same 使用：

* Passive
* Active
* Constructive
* Interactive

定义直接按 ICAP 原意：

* Passive：主要被动接收
* Active：有表面操作或简短回应
* Constructive：产生超出已有输入的新内容
* Interactive：与他人进行互相建构

说明：
在 EEDI 的单轮 student response 里，Interactive 可能并不常见，但必须保留。

---

#### 5.4.8 `response_commitment_state`

理论依据：

* Bandura self-efficacy
* Pekrun control appraisal
* metacognitive monitoring

方法层分类：

* `avoidant`
* `tentative`
* `committed`

定义：

* `avoidant`

  * 学生回避明确表态
* `tentative`

  * 学生愿意试探性表态，但保留明显不确定性
* `committed`

  * 学生愿意明确给出答案/判断

说明：
这是理论推导的实现构念，不是原理论原生类别。

---

#### 5.4.9 `response_maturity_cap`

理论依据：

* ICAP
* SRL
* 当前理解与内化状态

方法层分类：

* `fragment_only`
* `brief_local_explanation`
* `limited_structured_reasoning`
* `full_student_level_reasoning`

定义：

* `fragment_only`

  * 只能给片段、词语级或极短回应
* `brief_local_explanation`

  * 可给局部解释，但不成体系
* `limited_structured_reasoning`

  * 可给有限结构化解释
* `full_student_level_reasoning`

  * 可给较完整、相对成熟的学生层级推理

说明：
这是一个**行为上界变量**，不是理论原生类别，但必须受理论约束。


## 6. 三类动态失真（必须有理论依据）

本项目在动态越界检查中，重点检查三类失真。
它们不是理论原生标签，而是 **theory-derived diagnostic criteria**。

### 6.1 `over_fast_transition`

定义：
在教师支持强度不足的情况下，学生状态却不合理地快速跃迁到高水平理解、完整承诺或成熟推理。

理论依据：

* ZPD
* scaffolding
* internalization 的渐进性

说明：
弱提示后，学生可以发生局部更新，但不应直接从低理解跳到完整掌握。

---

### 6.2 `error_path_discontinuity`

定义：
学生原先持续暴露的误解或错误路径，没有经过合理扰动和逐步修正，就突然消失并切换成高度正确理解。

理论依据：

* conceptual change
* misconception continuity

说明：
真实学生的错误路径通常有连续性，概念改变往往是渐进扰动和重组。

---

### 6.3 `over_mature_response`

定义：
学生下一轮回复在解释深度、结构完整性、元认知清晰度或承诺强度上，明显超出其当前状态应允许的成熟度。

理论依据：

* ICAP
* SRL
* self-efficacy / control appraisal

说明：
如果学生当前还只处在表层吸收或弱监控状态，却输出高度完整、冷静、成熟的解释，这就是成熟化过度。

## 8. 哪些模块必须用 LLM，哪些必须规则主导

### 8.1 必须使用 LLM 的模块

#### `build_student_context_profile(...)`

理由：

* 这是基于理论的交互内生学生表征提炼
* 涉及对历史对话的语义解释
* 不能用 heuristics 替代

#### `build_tutor_move_profile(...)`

理由：

* 教师动作类型和强度是语义分析问题
* 不能用简单关键词或长度规则替代

#### `resolve_interaction_state(...)`

理由：

* 这是第三人称局部状态解析
* 是整个方法核心

#### `predict_state_transition(...)`

理由：

* 这是长链仿真的关键
* 需要推断“在当前帮助下学生下一步会怎么变”

#### `generate_student_turn(...)`

理由：

* 回复生成必须由 LLM 完成

#### `review_dynamic_violation_with_llm(...)`

理由：

* 仅用于边界样本复核
* 不能全量使用

---

### 8.2 必须规则主导的模块

#### `compile_constraints(...)`

* 将状态翻译成行为边界
* 规则主导

#### `check_hard_dynamic_violations(...)`

* 先做硬规则初筛
* 例如句数过长、明显完整成熟化、和约束显著矛盾

#### `retry_with_tighter_constraints(...)`

* 最多一次局部重试
* 不允许 LLM 决定是否无限重试

#### `evaluation.py`

* 所有统计、聚合、指标
* 必须规则主导

#### 数据读取与切分

* 必须规则主导

## 9. Prompt 设计原则（非常重要）

### 9.1 凡是理论原生有类别的，必须 exact same

例如：

* ICAP 的四类必须原样列出
* 不允许自造：

  * `active_low_constructive`
  * `semi_constructive`
  * `interactive_like`

### 9.2 凡是理论原生不是固定类别的，不得伪装成 low/medium/high

例如：

* Bandura
* Zimmerman
* Pekrun

这些理论在 prompt 中必须要求：

* 基于理论做描述性分析
* 给出理论化证据
* 不要假装成原生离散标签

### 9.3 方法层状态允许自定义，但必须定义清楚

例如：

* `competence_position`
* `misconception_status`
* `help_internalization_state`

这些是方法层状态，不是假装来自原理论。

## 10. 关键 prompt 模板要求

### 10.1 StudentContextProfile Prompt

必须：

* 明确说明 Bandura / Zimmerman / Pekrun 不是固定离散分类
* 让模型按理论做描述与证据抽取
* 对 ICAP 只能使用原生类别

### 10.2 TutorMoveProfile Prompt

必须：

* 明确说明是对教师动作做支架/帮助强度解析
* 不能直接回答题
* 不能使用“这轮应该让学生学会多少”这样的结果导向句式

### 10.3 InteractionState Prompt

必须：

* 不允许直接生成学生回复
* 只做第三人称状态解析
* 每个方法层状态都附定义
* 明确写出：

  * competence_position 的三类定义
  * misconception_status 的四类定义
  * engagement_form 的 ICAP 原生类别

### 10.4 StateTransition Prompt

必须：

* 不允许直接生成学生回复
* 只预测状态如何变化
* 要求模型明确考虑：

  * 当前状态
  * 教师动作类型与强度
  * 状态变化是否符合渐进内化逻辑

### 10.5 Answer Generation Prompt

必须：

* 明确禁止使用超出预测状态的知识
* 明确禁止表现出超过 `response_maturity_cap` 的成熟度
* 明确禁止为了拟合目标而“故意答成某种样子”

### 10.6 Dynamic Violation Review Prompt

必须：

* 明确三类失真定义
* 强调不是判对错，而是判状态一致性

## 11. 反作弊规则

必须明确禁止：

1. 根据真实下一轮学生回复反向提示模型
2. 根据真实状态或评测指标修改生成路径
3. 针对某些对话模板、题号、教师动作写特殊兜底
4. 根据教师发言中某些关键词直接硬编码 student state
5. 在 transition 逻辑中显式塞入“这一轮不该学会/应该学会”
6. 任何把 EEDI 真实标签带入 generation path 的行为

## 13. 给 Codex 的硬要求

你在实现时必须遵守：

1. 不得把非离散理论压成 low/medium/high 假装是原理论分类
2. 凡是理论原生类别，必须 exactly same
3. 方法层状态必须定义清楚，不得混淆成理论原生类别
4. 所有 prompt 必须可审计、可读、集中存放在 `src/prompts.py`
5. 所有核心状态与 transition 都必须显式对象化，不得藏在大段 prompt 文本里
6. 若效果不好，优先改：

   * 状态解析
   * 动作画像
   * 状态转移
   * 约束编译
     不得回退成 prompt patching

## 14. 项目成功标准

v1 成功不要求“完美模拟”，但至少要求：

1. 代码结构清楚，不是 prompt 补丁系统
2. 核心动态链路可跑：

   * Context -> State -> Transition -> Reply -> Violation
3. 方法上能解释三类失真
4. 新方法相较 direct roleplay，在：

   * 过快跃迁
   * 错误路径断裂
   * 成熟化过度
     上至少有可观察改进
